## `as const`

You might have already come across `as const` before. It's
one of my most used functionalities of TypeScript. 

In a nutshell, `as const` tells the compiler to infer the narrowest or most specific type it can for an expression. 

Let's have a look at the following example.
```typescript
const colorObject = {
  RED: "red",
  GREEN: "green",
}

type ColorObject = typeof colorObject
//   ^? type ColorObject = { RED: string; GREEN: string; }
```

As we can see, as type values we simply get `string`. Why is that?
Well, in JavaScript we can simply mutate the objects values. Hence
TypeScript can not infer the type more narrowly.

```typescript
// That's valid ✅
colorObject.RED = "blue"
```

Somehow we got to tell TypeScript, "Hey, this object can not be
mutated under any circumstances". 

Essentially, there are two main ways to tell that to TypeScript.

- Using [`Object.freeze()`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/freeze) that will
not only make the object immutable when running the TypeScript Compiler, but also during runtime.

- Using `as const`, that will tell the
TypeScript compiler that the given Object or Array shall never
be mutated.

Personally, most of the times I prefer `as const`, because there
is usually no reason for me to restrict the mutability during runtime.

By rewriting the codesnippet above, the benefit is apparent.

```typescript
const colorObject = {
  RED: "red",
  GREEN: "green",
} as const
// 👆 Note: As const

// ❌ Not allowed
colorObject.RED = "blue"

type ColorObject = typeof colorObject
//   ^? type ColorObject = { readonly RED: "red"; readonly GREEN: "green"; }
```

Now that we have added `as const` we get the actual strings as
values for the `ColorObject` type. With that, we can go even further
and, for instance, get a union type of all the `colorObject` values.

```typescript
type ColorObjectsKeys = keyof ColorObject
//   ^? type ColorObjectKeys = "RED" | "GREEN"
type Color = ColorObject[ColorObjectKeys]
//   ^? type Color = "red" | "green"
```

This even works for arrays!

```typescript
const breakpoints = ["xs", "sm", "md", "lg"] as const
type Breakpoint = typeof breakpoints[number]
// . ^? type Breakpoint = "xs" | "sm" | "md" | "lg"
```

## Change function return type depending on parameters

Sometimes it is useful to change the return type depending on the function
parameters. Let's have a look at this next example:

> **NOTE**: In order to reproduce this example, you need to enable
> `compilerOptions.strictNullChecks = true` in your `tsconfig.json`

```typescript
// We can expect `translations` is a object of the structure Record<string, string>
import translations from "translations.yml"

function getTranslation(key: string, fallback?: string) {
  return translations[key] || fallback;
}

const res1 = getTranslation("goodbye");
//    ^? const res1: string | undefined
//    ✅ Correct, the result might be string or might be undefined


const res2 = getTranslation("goodbye", "Good bye");
//    ^? const res2: string | undefined
//    ❌ Incorrect, the result can only be a string
```

`getTranslation()` is a function that will try to return the translation of the given
`key`. If the translation can not be found, it will use the given `fallback` that can
be passed optionally as second argument.

If we look at `res2` & the implementation of `getTranslation()` we can actually
be sure that the result should always return `string`. So how do we fix this?

One method I like to use is method overloading. Overloading has many uses
but in this particular case I would like to teach TypeScript "in case `fallback` is actually defined, return `string`".

Let's have a look how we can do this.

```typescript
function getTranslation(key: string, fallback: string): string;
function getTranslation(key: string, fallback?: string): string | undefined;
function getTranslation(key: string, fallback?: string) {
  return translations[key] || fallback;
}

const res1: string | undefined
//    ^? const res1: string | undefined
//    ✅ Correct, the result might be string or might be undefined

const res2 = getTranslation("goodbye", "Good bye");
//    ^? const res2: string
//    ✅ Correct, the result is always a string
```

Now we have the correct type as a result (in this case*) 🎉

### The downsides of using explicit return types and function overloads

This secret super move comes at a high price & should be used cautiously.
The function overloads are closely coppled to the actual logic of the function itself which isn't a good practice.
When you explicitely define types you can lie about the types. The implementation
on the other hand can't lie. 

Let's say, if we change it so that the `fallback` is not taken into
account anymore in the actual implementation we actually get a wrong return type

```diff
function getTranslation(key: string, fallback: string): string;
function getTranslation(key: string, fallback?: string): string | undefined;
function getTranslation(key: string, fallback?: string) {
-  return translations[key] || fallback
+  return translations[key]
}

const res1 = getTranslation("goodbye");
//    ^? const res1: string | undefined
//    ✅ Still correct

const res2 = getTranslation("goodbye", "Good bye");
//    ^? const res2: string
//    💣💣💣 That's wrong! It can be undefined
```

In this example the function overloads are actually harmful, which might cause
an actual bug in production. No errors from TypeScript. Everything is green.

Yeah... You're playing with fire. Sometimes it's warranted to play with fire (e.g. as a library author to provide better DX), 
sometimes it's just the better route to do an additional null check even though technically it wouldn't be needed.


## Going buckwild with generics

With this next example I want to get our hands dirty with generics.
This is the advanced part of the article. If you loose your mind over it
at first, don't worry, me too.

What we want to achieve is a regex function, that returns the exact amount of
capturing groups of a given regular expression.

```typescript
function tsRegex(reg: string, value: string) {
  const regex = new RegExp(reg, "i");
  const result = value.match(regex)
  if(result) {
    return [...result];
  }
  return null;
}

// What we would like to achieve:

const res1 = tsRegex("(.*): (.*)", "foo: bar")
// ℹ️ The function will return 3 strings:
//    - The first one is the matched string
//    - The second one is the first capturing group (so foo)
//    - The third one is the third capturing group (so bar)

// Therefore the type for res1 should be: [string, string, string] | null
// Actual type for res1: string[] | null
```

If I were to write this functionality in JavaScript it would look something along the lines of
this:
 
```typescript
const regex = "(.*): (.*)";
const output = ["string"];

const chars = regex.split("");

let isInCapturingGroup = false;
for (const char of chars) {
  if (char === "(") {
    isInCapturingGroup = true;
  }
  if (char === ")") {
    output.push("string");
    isInCapturingGroup = false;
  }
}

console.log(output);
// Log: ['string', 'string', 'string']
```

Now how the hell do we translate this to the TypeScript type system?

### Narrowly infer function arguments

Okay let's get started. First of all, we somehow need to infer the _actual_
string value of the first argument `reg`. We can do this by using a simple generic.
In order to still restrict the first argument to a `string` we can use the `extends`
keyword.

```diff
- function tsRegex(reg: string, value: string) {
+ function tsRegex<TInput extends string>(reg: TInput, value: string) {
```

The generic argment `TInput` will now be able to infer and narrow the given `reg` string.
We can test this with the following example:

```typescript
function tsRegex<TInput extends string>(reg: TInput, value: string): TInput {
  return reg
}
const res = tsRegex("(.*): (.*)", "foo: bar");
//    ^? const res: "(.*): (.*)"
//     ℹ️ It's not just a type `string` but the actual given string value as type
```


### Iterate over each character

If we have a look back at my JS example, iterating over each character
of a given string is really simple.

```javascript
const chars = regex.split("");

for (const char of chars) {
```

In the type system we do not really have loops though. But we have the possibility of
creating recursions!

```typescript
type Regex<TInput> = Regex<TInput>
```

Now off course this will create an infinite recursion and TypeScript even hints at that.
In order to stop the recursion we can use conditional types. 

```typescript
type Regex<TInput> = TInput extends string ? true : Regex<TInput>
```

Now if the given generic argument `T` extends a string we immediately "return"
`true`, otherwise we continue recurisvely call the generic (...which will 
result in another infinite recursion in this example but you get the picture)

Okay so we can create a finite loop of some sorts. So what's left is splitting
the string into single characters and iterating over each of them

```typescript
type Regex<TInput> =
  TInput extends `${infer First}${infer Rest}`
    ? HasOpeningBracket<Rest>
    : false;
```

With this conditional we can match the first character and store into the
`First` type variable and match the rest of the characters as `Rest`. 

So what this recursion does, is loop over every single character
and once we have reached the end of the string we "return" false.

Therefore at the moment this generic type will always "return" false.

```typescript
type A = Regex<"string">
//   ^? type A = false
```

Though we can now proceed and do additional conditions for each character.
